# Translations (i18n)

renCal's UI text is translated with [Lingui](https://lingui.dev). English is the
source language: the text in the code is the message id, and the English
catalog needs no translations.

## How the language is chosen

At startup, before the first render, `activateSystemLocale()` in `src/lib/i18n`
picks the locale in this order:

1. `language` in `~/.config/rencal/config.toml`, e.g. `language = "de"` or `"de-AT"`
2. the WebView's languages (on Linux: `LANG` / `LC_MESSAGES`)
3. `en-GB`

The first entry whose language has a catalog wins. The full tag (with region)
drives dates and weekday/month names through `Intl`, so `de-AT` shows "Jänner".
A change to `language` applies at the next start.

## Adding a language

1. Add the language code to `CATALOG_LANGUAGES` in `src/lib/i18n/catalog-languages.ts`.
2. Run `just i18n-extract`. This creates `src/locales/<lang>/messages.po`.
3. Translate every `msgstr` in that file (any PO editor works: Poedit, Weblate, Lokalize).
4. Run `pnpm i18n:check`. It fails while translations are missing.

## Writing translatable code

- Use the core macros: `import { t, msg, plural } from "@lingui/core/macro"`.
- `t` only at render time, inside a component or function. Text in module-level
  constants is a `msg` descriptor, rendered with `i18n._(descriptor)`
  (`import { i18n } from "@lingui/core"`). ESLint enforces this (`lingui/t-call-in-function`).
- No `<Trans>` or `useLingui`: there is no `I18nProvider`; the global instance
  is activated before the first render, and in tests by `src/test-setup/i18n.ts`.
- Keep whole sentences in one message, with named variables: ``t`Delete ${name}?` ``.
- Plurals: `plural(count, { one: "# event", other: "# events" })`.
- Short, ambiguous words get a context: `t({ message: "Week", context: "view name" })`.
- Dates, weekday and month names come from `@/lib/event-time` (`formatShortDate`,
  `weekdayNames`, …), never from a catalog.
- Text that is not UI (key names, ids, log messages) stays as is.
  If `lingui/no-unlocalized-strings` flags it, disable the rule for that line
  with a reason.

After changing UI text, run `just i18n-extract` and translate the new entries.
`just test` runs `pnpm i18n:check`, which fails when the catalogs are out of
sync with the code or a translation is missing.

## Quick-add parser

The natural-language input ("Meeting tomorrow at 3pm") has its own words per
language in `src/lib/magic-parser/vocabularies/`: chrono-node's grammar for
that language plus recurrence phrases ("jeden Montag", "täglich"), location
words and connectors. These are parser input, not catalog entries. The parser
tries the UI language first and English after it, and keeps the reading that
recognises the most text. To support a new language, add a vocabulary file
(chrono-node ships grammars for de, es, fr, it, ja, nl, pt, ru, sv, uk, zh)
and register it in `src/lib/magic-parser/index.ts`; then translate the
examples "Meeting at 3pm" and "e.g. "5 Sep"…" with phrases that parse.

## Architecture

`src/lib/i18n` is a small bounded context:

- Domain: `Locale` (value object, accepts `de_DE.UTF-8` and `de-DE`) and
  `negotiateLocale`.
- Use case: `activateUserLocale`, which only knows its ports (`ports.ts`).
- Adapters: `ConfigTomlLanguage`, `NavigatorPreferredLocales`,
  `PoCatalogLoader`, `LinguiActivator`.
- `index.ts` wires the adapters together; `main.tsx` calls it.

Not translated yet: the native macOS menu (`src-tauri/src/menu.rs`) and error
texts produced by the Rust backend.
